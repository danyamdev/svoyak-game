# AGENTS.md

## Проект

«Своя игра» — локальное React-приложение для проведения викторины ведущим с
одного устройства. Поддерживаются отдельные игроки и команды, три раунда 5×5,
спецвопросы, финал, редактор пакета и восстановление из `localStorage`.

Перед первым изменением кода в сессии прочитай `PROJECT_RULES.md`, если он ещё не
загружен в контекст. Не меняй зафиксированные там соглашения без согласования.

## Стек

React 19, TypeScript 6, Vite, React Router, Zustand, Zod, Radix UI, SCSS Modules,
Vitest, ESLint, Stylelint и Prettier. Менеджер пакетов — Yarn 1.

## Архитектура

- `src/domain/game` — модели, правила и чистая игровая машина; без React и Zustand.
- `src/features` — хранилища, persistence, миграции и импорт/экспорт пакета.
- `src/pages` — страницы маршрутов.
- `src/widgets` — крупные составные блоки страниц.
- `src/shared/ui` — переиспользуемые UI-компоненты без игровой логики.
- `src/app` — маршрутизация, глобальные стили и запуск приложения.

Импортируй соседний модуль через его `index.ts`. Доменную логику тестируй без UI.
Состояние меняй через команды игровой машины или действия соответствующего store.

## Код

- Используй строгие типы; `any` допустим только с явным обоснованием.
- JSX — в `.tsx`, остальное — в `.ts`.
- Локальные стили — только `*.module.scss`; общие токены находятся в
  `src/app/styles/global.scss`.
- Комментарий нужен для причины, ограничения, миграции или сложного правила, а не
  для пересказа кода.
- Сначала переиспользуй существующий компонент или функцию. Не вводи абстракцию
  ради одного простого случая.
- Не добавляй зависимости без объяснения пользы и согласования существенного
  расширения стека.

## Работа с контекстом

1. Для текущего состояния при необходимости прочитай `docs/progress.md`.
2. Найди символы и файлы через `rg`/`rg --files`; открывай только релевантные
   фрагменты.
3. Не перечитывай весь репозиторий и не повторяй известную архитектуру.
4. Вноси минимальные целевые изменения; не рефактори посторонний код.
5. Обновляй только документ, являющийся источником истины для изменённой области.

## Проверки

- Во время работы запускай ближайший тест или точечный линтер.
- После законченной кодовой задачи выполняй `yarn validate`, как требует
  `PROJECT_RULES.md`.
- Для изменений только Markdown достаточно проверить формат и ссылки; явно
  сообщи, если сборка не запускалась.
- Новую игровую ветку покрывай тестом перехода состояния; новую миграцию — тестом
  восстановления старого формата.

## Формат задачи

Для нетривиальной задачи кратко зафиксируй цель, затрагиваемые модули, результат и
критерии готовности. В завершении сообщи только: что изменено, какие проверки
прошли и следующий шаг. Продуктовые правила, UX-компромиссы и дизайн согласуй до
крупной реализации.
